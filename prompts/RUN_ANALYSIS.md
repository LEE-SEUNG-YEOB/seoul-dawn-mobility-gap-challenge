# 새벽 이동 공백 데이터 분석 실행 프롬프트

이 저장소에서 새벽 이동 공백 데이터 분석을 시작하라.

## 반드시 지킬 범위

사용자는 데이터 분석만 담당한다. 공모전용 분석 기획서, 참가신청서, 정책 제안서, 발표 원고 또는 제출용 서사를 작성하지 마라. 다른 팀원이 별도로 기획서를 작성할 수 있도록 재현 가능한 코드, 데이터 출처, 데이터 사전, 검증된 표·지도·그림, 가정, 불확실성, 한계와 실행 명령만 제공하라.

핵심 질문은 다음과 같다.

> 새벽버스를 추가로 도입하거나 첫차를 조정한다면 어느 구간부터 지원해야 하는가?

## 시작 절차

계획만 설명하고 멈추지 마라.

1. `AGENTS.md`와 `.agents/roles/*.md`를 읽고 모든 지침을 적용하라.
2. `docs/context/`의 원본 두 파일과 `PROJECT_CONTEXT.md`를 읽어 연구 질문, 데이터 후보, 한계를 확인하라.
3. 기존 파일과 Git 상태를 확인하고 사용자 변경을 보존하라.
4. 공모전·데이터 페이지의 현재 조건이 분석에 영향을 주면 공식 원문에서 최신 상태를 확인하라.
5. 멀티에이전트 기능이 지원되면 사용자에게 다시 묻지 말고 생성 도구를 **실제로 호출**하여 Wave 1의 `data_steward`를 즉시 생성하라.
6. `data_steward`가 `data/metadata/analysis_contract.json`과 `outputs/intermediate/data_audit/readiness.json`을 만들고 검증 명령을 통과하면 메인이 계약과 준비 상태를 승인하라.
7. Wave 2에서 `mobility_demand_analyst`와 `transit_access_analyst`를 실제 생성해 서로 다른 파일에서 병렬 작업하게 하라. 준비 상태가 제한되거나 `blocked`여도 두 역할은 생성하되, 허용되지 않은 실증 계산은 금지하고 코드·테스트·차단 근거만 만들게 하라.
8. 각 생성 메시지에 역할 파일 전문 또는 그 파일을 반드시 읽으라는 지시, 승인된 계약·준비 상태, 담당 질문, 입력, 수정 가능 경로, 고정 산출물, 검증 명령과 완료 조건을 포함하라.
9. 결과를 기다린 뒤 메인이 `candidate_id`로 검수·통합하라.
10. 통합 후 `qa_reviewer`를 실제 생성해 재현성, 수치, 지도, 가정, 준비 모드와 산출 범위의 일관성을 독립 검증하게 하라. QA 지적을 수정한 뒤 재검증하라.

멀티에이전트 기능이 없으면 생성했다고 가장하지 말고, 네 역할을 메인이 순차 수행한 사실과 이유를 `reports/agent_runs/`에 남겨라.

## 메인 에이전트 책임

메인 에이전트 `analysis_lead`는 최종 방법론 선택, 공통 설정과 통합 코드, 결과 통합, 검증, 재현 실행, Git 커밋과 팀원 인계를 직접 책임진다. 서브에이전트 결과를 그대로 복사하지 말고 출처·수치·가정·경로 충돌을 확인하라.

`mobility_demand_analyst`는 수요 측 후보만 만들고 서비스 공백을 판정하지 않는다. `transit_access_analyst`만 정류장별 첫차·환승·보행·서비스 캘린더를 적용해 계획 시각 기준 서비스 공백 후보를 판정한다. 입력이 불완전하면 `no_gap`이 아니라 `unknown`으로 두며, 직접 검증 자료가 없으면 실제 미충족 수요라고 부르지 않는다.

## 분석 결과

확보 가능한 실제 자료를 사용해 다음을 산출하라.

- 03:00~06:00 OD 흐름과 이동 집중도
- 생활이동은 있으나 현재 첫차·환승으로 제시간 도착이 어려운 후보
- 첫차 조정 우선 노선·정류장 후보표
- 현행, 첫차 15분 조정, 30분 조정, 새벽 단축노선 추가의 동일 조건 비교
- 조정 전후 도착 가능 지역 지도
- 추가 운행시간당 예상 수혜 인원
- 승용차·택시에서 버스로의 전환율별 탄소 변화 민감도
- 분석 가정, 불확실성, 한계, 데이터 계보와 재현 명령

공개 자료가 1시간 단위이면 15분과 30분의 차이를 정밀 검증한 것처럼 표현하지 마라. 250m·20분 자료나 설문을 확보하지 못하면 공개 데이터 기반 후보 탐색 결과와 추가 검증 필요 항목을 분리하라. 새벽 이동자를 새벽 근로자로 단정하지 말고, 관찰 자료로 인과관계를 주장하지 마라.

준비 상태의 `mode`에 따라 산출 범위를 제한하라.

- `full`: 통합 시나리오와 우선순위까지 생성
- `demand_only`: OD·수요 후보만 생성하고 서비스 공백·우선순위·수혜/차량시간은 `unsupported`
- `transit_only`: 시간표 기반 접근성 기술 점검만 생성하고 수요 가중 효과·우선순위는 `unsupported`
- `blocked`: 출처·차단 근거·대체재와 수집·검증 코드·테스트만 생성하고 실증 완료라고 보고하지 않음

`reports/analysis_coverage.md`에 요청 결과별 `produced|unsupported`, 누락 의존성, 영향, 다음 확보 단계와 `COMPLETE_FULL|COMPLETE_LIMITED|BLOCKED_INPUT` 상태를 기록하라.

## 작업 권한

프로젝트 루트 내부의 안전한 작업, 공개 무인증 데이터의 합리적 크기 다운로드, 테스트, 결과 생성과 일반 Git 커밋은 승인 없이 수행하라. 위험하거나 되돌리기 어려운 작업, 프로젝트 밖 접근, 인증·결제·개인정보·불명확한 라이선스, 대규모 다운로드, 외부 제출·게시·배포는 먼저 승인받아라.

일반 커밋은 자유롭게 하되 커밋마다 관련 변경만 포함하라. 사용자가 푸시까지 요청하지 않았다면 원격에 푸시하지 마라. 강제 푸시와 Git 기록 재작성은 하지 마라.

## Git 추적 규칙

`.gitignore`를 임의로 광범위하게 바꾸지 마라. 특히 `*.md`, `*.txt`, `*.docx` 전체 무시 규칙을 만들지 마라. 다음 파일은 반드시 Git 추적 대상으로 유지하라.

- 주제 원본과 데이터 확보처 원본
- `AGENTS.md`와 서브에이전트 역할 파일
- 이 실행 프롬프트
- README, 환경·의존성 파일, 데이터 사전·출처 매니페스트
- 분석 코드·테스트와 팀원이 사용할 결과표·그림·지도·인계서

대용량 원자료, 인증정보, 캐시, 임시 파일과 로컬 QA 로그만 제외하라. 무시 파일을 강제 추가하지 말고 커밋 전 `git status --ignored`, `git diff --check`, `git check-ignore -v`로 확인하라.

## 종료 조건

다음 조건을 모두 만족할 때만 작업 완료로 보고하라.

1. 실제 데이터와 출처가 추적 가능하다.
2. 파이프라인과 핵심 결과가 재현된다.
3. 메인 검수와 독립 QA가 끝났다.
4. 분석 코드, 결과, 가정, 한계와 실행법이 팀원에게 인계 가능하다.
5. 분석 기획서나 제출용 서사를 작성하지 않았다.
6. Git 상태와 커밋 내용을 확인했다.
